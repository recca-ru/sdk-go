# Приёмка в песочнице: `cpatest.Conformance`

Короткая версия лежит в [README, шаг 10](../README.md#шаг-10-пройти-приёмку-в-песочнице).
Здесь подробности: что именно набор делает, какие опции и переменные
окружения у него есть и как читать результат.

## Зачем это нужно

Тестовый стенд `cpatest.NewServer` доказывает, что ваш код **собирает верные
запросы и разбирает верные ответы**. Но стенд не воспроизводит поведение
платформы: срок холда, тройку ставок, идемпотентность настоящего сервера,
права партнёра, лимиты и гео. Числа в его ответах выдуманные. Это предмет
песочницы, и набор `Conformance` проверяет именно её.

Набор проходит четыре цепочки и сверяет подписи:

1. самопроверка (`Self.Get`);
2. каталог офферов;
3. вертикаль «партнёр → ссылка → переход → конверсия → повтор конверсии»;
4. выплата.

Каждый шаг печатает `request_id`, поэтому вывод `go test -v` и есть протокол
приёмки.

## Защита от боя

Набор работает **только** с песочницей и стендом. До первого запроса он
сверяет адрес клиента: разрешены песочница и петля (`127.0.0.1`, `localhost`,
`[::1]`). На любом другом адресе набор отказывается и **не шлёт ни одного
запроса**. Флага «разрешить бой» нет.

Второй ремень: `GET /cpa/self` называет среду (`SelfInfo.Environment`), и если
это не `sandbox`, набор останавливается до первой записи. Адрес можно
направить не туда прокси или DNS, а ответ сервера о самом себе подделать
нельзя.

Причина строгости: набор создаёт данные, а клиент с пустым `Environment` ходит
в бой. Забытая настройка при боевом ключе создавала бы настоящего партнёра,
заказ и заявку на выплату при каждом прогоне вашего CI.

## Что набор создаёт за прогон

- партнёра (по умолчанию `conformance-webmaster`);
- ссылку и переход;
- подтверждённую конверсию на 2 500 ₽ под номером `conformance-order-<метка>`;
- если баланс позволяет, заявку на выплату на сумму порога выплаты партнёра.

Номера заказов и ключ перехода уникальны на прогон.

## Цепочка выплат и баланс

Набор читает `Partners.Balance` и идёт по `CanRequest`:

| `CanRequest` | Что ждёт набор | Итог |
|---|---|---|
| `true` | заявка принята, повтор с другой суммой даёт `409 IDEMPOTENT_MISMATCH` | зелёный. Если сервер отказал `INSUFFICIENT_BALANCE`, красный: `can_request` врёт |
| `false` | заявка отбита `409 INSUFFICIENT_BALANCE` | зелёный, в журнале теста строка «положительная ветка выплаты не измерена: доступно X, порог Y». Если сервер заявку принял, красный: баланс врёт |

У свежего партнёра песочницы всё лежит в холде, поэтому обычно измеряется
вторая строка. Положительная ветка измерится, когда холд созреет и доступная
сумма дорастёт до порога.

## Опции

```go
cpatest.Conformance(t, client, cpatest.ConformanceOptions{
	PartnerExternalID: "my-test-partner", // под кем идти
	OfferID:           "off_...",         // на каком оффере
	ExternalIDPrefix:  "acme",            // префикс номеров заказов
	SkipPayouts:       false,             // true: пропустить выплаты целиком
})
```

`SkipPayouts` нужен редко: партнёр без одобренного баланса набор не роняет.
Включайте только если на площадке нельзя создавать заявки вовсе.

## Сценарии приёмки по договору

Общие цепочки выше проверяют библиотеку и сервер. Сценарии 1–4 и 6
дополнения к Приложению № 1 проверяют свойства конкретных офферов и
включаются опцией `Scenarios`, каждому свой оффер:

```go
cpatest.Conformance(t, client, cpatest.ConformanceOptions{
	Scenarios: &cpatest.ScenarioOptions{
		BrandOfferID: "…", BrandGoal: "brand_registered", // 1: бренды и блогеры
		GoalOfferID:  "…", Goal: "sale",                  // 3: целевое действие
		RevshareOfferID: "…",                             // 2 (скаут) и 4 (revshare)
		MultiOfferID: "…", MultiGoal: "multi",            // 6: несколько конверсий
		MultiPlainGoal: "single",                         //    с одного перехода
	},
})
```

Ожидаемые суммы набор выводит из условий оффера, которые отдаёт сам сервер.
В песочнице офферы приёмки уже заведены; их идентификаторы Recca передаёт
вместе с ключом.

⚠ Смену статуса по истечении холда (сценарий 3) набор в том же прогоне не
измеряет: её доказывает вебхук `cpa.conversion.approved`, пришедший после
холда.

Сценарий 6 требует на одном оффере пару целей: `MultiGoal` с включённым
оператором флагом «несколько конверсий с одного перехода» (каждый заказ той же
цели с того же перехода платится своей конверсией) и `MultiPlainGoal` без него
(второй заказ пары получает `409 ALREADY_CONVERTED`). Флаг включает оператор
сети, набор его только читает из обеих проекций оффера, и расхождение
проекций красит приёмку.

## Запуск против песочницы из репозитория SDK

```sh
RECCA_CPA_SANDBOX_KEY=<ключ арендатора песочницы> go test -run TestConformanceAgainstSandbox -v .
```

Без ключа тест пропускается с объяснением (`SKIP` виден в выводе): «не
проверено» не должно читаться как «проверено».

| Переменная | Что задаёт |
|---|---|
| `RECCA_CPA_SANDBOX_KEY` | ключ арендатора песочницы (обязательно) |
| `RECCA_CPA_SANDBOX_PARTNER` | под каким партнёром идти |
| `RECCA_CPA_SANDBOX_OFFER` | на каком оффере |
| `RECCA_CPA_SANDBOX_BRAND_OFFER`, `RECCA_CPA_SANDBOX_BRAND_GOAL` | сценарий 1 |
| `RECCA_CPA_SANDBOX_GOAL_OFFER`, `RECCA_CPA_SANDBOX_GOAL` | сценарий 3 |
| `RECCA_CPA_SANDBOX_REVSHARE_OFFER` | сценарии 2 и 4 |
| `RECCA_CPA_SANDBOX_MULTI_OFFER`, `RECCA_CPA_SANDBOX_MULTI_GOAL`, `RECCA_CPA_SANDBOX_MULTI_PLAIN_GOAL` | сценарий 6 |
| `RECCA_CPA_SANDBOX_SKIP_PAYOUTS` | `1`, если на площадке нельзя создавать заявки |

⚠ Ключ в вывод не попадает: набор его не печатает, а клиент маскирует в
отладке.

Прогон создаёт в песочнице данные, поэтому его запускают руками, а не в
каждой сборке.
